## B1. Proyectos open-source de agendamiento (Cal.com / Cal.diy, Easy!Appointments, otros): licencia, WhatsApp, self-hosting y viabilidad en un fin de semana

### Takeaway
**Cal.com cerró su código el 15 de abril de 2026.** Lo público quedó como **Cal.diy, 100% MIT**, pero sin Workflows (donde vivían los recordatorios automáticos), Teams, Insights, SSO ni API v1, y su README lo recomienda solo para uso personal y no productivo. Easy!Appointments es GPL-3.0 (PHP/MySQL), con sincronización de Google Calendar y notificaciones por email, sin WhatsApp en su lista de funciones. Ninguno trae WhatsApp listo. Para un fin de semana es más realista un agendamiento propio mínimo o consumir uno de estos vía API que hacer fork.

## B3. Librerías de WhatsApp: SDK/wrappers de la Cloud API oficial vs. no oficiales (Baileys, whatsapp-web.js, Evolution API, WAHA): licencia y riesgo de ToS/baneo

### Takeaway
Las librerías no oficiales (Baileys MIT, whatsapp-web.js Apache-2.0, WAHA Apache-2.0, Evolution API Apache-2.0 con condiciones extra) son libres y gratuitas, pero automatizan WhatsApp Web contra los Términos de WhatsApp. Sus propios READMEs advierten del bloqueo, y hay reportes de baneos en 2026. Para un número real de una profesional de salud, lo correcto es la **WhatsApp Cloud API oficial** (plantillas aprobadas, costo por mensaje bajo en Colombia) con wrappers comunitarios MIT (`whatsapp-api-js`, `pywa`). El SDK oficial de Meta para Node está **archivado**. La política de IA de Meta de 2026 prohíbe chatbots de IA de propósito general en la API de negocio, pero permite bots de tareas como recordatorios de citas.

## B4. Implicaciones de compatibilidad de licencias para el repo propio

### Takeaway
Con Cal.diy ahora MIT, el temido "contagio AGPL" de Cal.com ya no aplica al código actual. Solo aplicaría si se parte de un snapshot anterior al 15 de abril de 2026, o si se usa Rallly (AGPL-3.0). Hacer fork o redistribuir código GPL-3.0 (Easy!Appointments, OpenEMR, LibreBooking) obliga a licenciar la obra derivada bajo GPL-3.0. Con dependencias MIT/Apache-2.0 (Cal.diy, Baileys, whatsapp-web.js, WAHA core, whatsapp-api-js, pywa, Medplum, Ollama), el repo propio puede ser MIT o Apache-2.0.

### Cited Findings
- Licencias verificadas el 2026-10-02 (archivo `LICENSE` en la rama por defecto): Cal.diy MIT — [calcom/cal.diy](https://github.com/calcom/cal.diy); Easy!Appointments GPL-3.0 — [alextselegidis/easyappointments](https://github.com/alextselegidis/easyappointments); OpenEMR GPL-3.0 — [openemr/openemr](https://github.com/openemr/openemr); LibreBooking GPL-3.0 — [LibreBooking/librebooking](https://github.com/LibreBooking/librebooking); Rallly AGPL-3.0 — [lukevella/rallly](https://github.com/lukevella/rallly); OpenMRS core MPL-2.0 — [openmrs/openmrs-core](https://github.com/openmrs/openmrs-core); Bahmni apps MPL-2.0 — [Bahmni/openmrs-module-bahmniapps](https://github.com/Bahmni/openmrs-module-bahmniapps); Medplum Apache-2.0 — [medplum/medplum](https://github.com/medplum/medplum); Baileys MIT — [WhiskeySockets/Baileys](https://github.com/WhiskeySockets/Baileys); whatsapp-web.js Apache-2.0 — [pedroslopez/whatsapp-web.js](https://github.com/pedroslopez/whatsapp-web.js); WAHA Apache-2.0 — [devlikeapro/waha](https://github.com/devlikeapro/waha); Evolution API Apache-2.0 + condiciones adicionales — [EvolutionAPI/evolution-api](https://github.com/EvolutionAPI/evolution-api); whatsapp-api-js MIT — [Secreto31126/whatsapp-api-js](https://github.com/Secreto31126/whatsapp-api-js); pywa MIT — [david-lev/pywa](https://github.com/david-lev/pywa); Ollama MIT — [ollama/ollama](https://github.com/ollama/ollama); SDK Node de Meta: licencia propia de Meta, archivado — [WhatsApp/WhatsApp-Nodejs-SDK](https://github.com/WhatsApp/WhatsApp-Nodejs-SDK)
- El relicenciamiento de Cal.com de AGPL-3.0 a MIT (Cal.diy) ocurrió el 15 de abril de 2026 — [implicator.ai](https://www.implicator.ai/cal-com-goes-private-as-self-hosted-calendly-choices-narrow-in-2026/)

### Inferences
- Tabla práctica (inferencia basada en los términos estándar de cada licencia):
  - **MIT / Apache-2.0** (Cal.diy, Baileys, whatsapp-web.js, WAHA core, whatsapp-api-js, pywa, Medplum, Ollama): se pueden usar o modificar dentro de un repo bajo cualquier licencia, conservando avisos de copyright (y el `NOTICE` en Apache-2.0). Apache-2.0 es compatible con GPL-3.0/AGPL-3.0, pero no con GPL-2.0-only.
  - **GPL-3.0** (Easy!Appointments, OpenEMR, LibreBooking): si se modifica y distribuye, la obra derivada debe ser GPL-3.0. Desplegarlos como servicio aparte y hablarles por HTTP desde el código propio normalmente no convierte el código propio en derivado (zona gris; no es asesoría legal).
  - **AGPL-3.0** (Rallly; Cal.com previo a abril de 2026): además obliga a ofrecer el código fuente a los usuarios que interactúan por red con la versión modificada. Si el repo va a ser público de todos modos, el costo práctico es bajo, pero fija la licencia del conjunto derivado en AGPL-3.0.
  - **MPL-2.0** (OpenMRS, Bahmni): copyleft por archivo; se puede combinar con código propio bajo otra licencia si los archivos MPL modificados siguen bajo MPL.
  - **Evolution API**: no es una licencia OSI pura por las condiciones extra (logo y aviso de uso). Si se integra, hay que cumplirlas o evitarla.
  - **SDK de Meta**: licencia restringida al uso con servicios de Facebook y además archivado. Mejor no usarlo como base.
- Recomendación de licencia para el repo propio: **MIT o Apache-2.0** si solo se usan dependencias permisivas, lo que maximiza la reutilización por otros fonoaudiólogos o desarrolladores. **AGPL-3.0** solo si se busca que cualquier SaaS derivado siga siendo abierto. Cualquiera de las dos encaja con el "why open innovation matters" del post.
- El modelo de IA tiene su propia licencia: los pesos de Gemma se distribuyen con términos propios de Google, no con una licencia OSI clásica (conocimiento previo, no verificado aquí). Conviene mencionarlo con transparencia en el post, porque el tema del reto es "open-source AI".
